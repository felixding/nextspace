# GNUstep platform integration for Chromium and Firefox

Keep the browsers' Linux backends and connect their existing platform interfaces to GNUstep. Use the current NativeUI host for native menus, panels, input interpretation and control drawing. Let the browsers keep their page layout, editing transactions and DevTools state. Compare this route with the working preview before retiring any of its widget adapters.

## What the browsers do

[Mac text input](https://chromium.googlesource.com/chromium/src/+/main/docs/ui/input_event/index.md), [LinuxUi](https://github.com/chromium/chromium/blob/main/ui/linux/linux_ui.h), [GTK implementation](https://github.com/chromium/chromium/blob/main/ui/gtk/gtk_ui.cc) | Gecko's Cocoa adapter translates selectors into Gecko editing commands. The upstream interfaces are candidates for integration. Their availability and call coverage on those builds must be verified individually. ## Proposed ownership

1. **Use desktop protocols first.** Keep the Wayland compositor responsible for window placement and decorations. Reuse the [FileChooser portal](../Libraries/NativeUI/Portal/README.md) for open/save panels and [D-Bus menu bridge](../Experiments/DBusMenus/README.md) for applications that export menus. Reuse the existing NativeUI menu path for Chromium's menu model and Firefox's GTK context-menu models. GNUstep tracks and draws the menus. Each browser owns item availability and executes its original actions.
2. **Route editing commands into the original editor.** Reuse the GNUstep responder and menu matching behind the shared command filter. Resolve the focused editing context and ask GNUstep for a command such as Select All or Undo. The adapter translates the command to the editor's existing action, preserving its selection and undo history. Prefer Chromium's `LinuxUi` and Gecko's `NativeKeyBindings` boundaries for browser and document editors. DevTools also needs a small editor-level adapter where CodeMirror handles the keystroke itself. Map commands to actions once at that boundary. Leave composition, ordinary typing, completion and console-specific handling on their existing paths. Both the key and the native menu item must dispatch the same edit operation once. Browser commands such as New Tab still use the browser's original action registry and native menu key matching. [Shared command filter](../Libraries/NativeUI/GNUstep/ViewHost.m)
3. **Integrate appearance separately.** Feed GNUstep colors, fonts and sizing into existing browser theme interfaces and shared DevTools styles. Keep developer-tool layouts and code rendering coherent. Where literal native appearance matters, such as left-side scrollers or standard buttons, keep the effective GNUstep drawing and metrics in [NativeUI](../Libraries/NativeUI/README.md) while the engine retains web layout, accessibility and state. Theme values alone cannot reproduce tracking, focus or behavior that the native control owns.

GNUstep's AppKit compatibility makes it a good implementation for these services. The macOS browser backends also rely on Apple frameworks and compile into different targets. The Linux backends already give us the useful boundaries. Standard desktop protocols are the broadest route for unchanged browser builds. Private browser integration points need build-specific qualification. Durable first-class support beyond those builds would require a supported integration interface or upstream changes. [GNUstep AppKit](https://www.gnustep.org/resources/documentation/Developer/Gui/Reference/index.html), [Chromium Linux toolkit setup](https://github.com/chromium/chromium/blob/main/chrome/browser/ui/views/chrome_browser_main_extra_parts_views_linux.cc), [Gecko platform build](https://github.com/mozilla-firefox/firefox/blob/main/widget/gtk/moz.build)

The command bridge should use the focused editor's existing validation and transaction rules. Word boundaries, multi-selection and undo grouping can still differ between GNUstep and CodeMirror. That is acceptable for macOS-style integration and must be measured wherever exact behavior is required. A shared desktop service also gives GTK and Qt clients a place to connect when their platform APIs expose the same operation.

## First comparison

Use the console prompt as the proving ground. Chromium's private resource adapter already selects the bundled DevTools host menu path. Firefox's adapter handles DevTools menu tooltips and already has a [GTK model bridge](../Libraries/NativeUI/Bridge/GtkContextMenus.inc). Check where each console edit menu goes, then attach the focused editor's actions there. Run with the current editor and widget substitutions disabled for that DevTools surface. Compare both variants under the same GNUstep settings.

The integration earns its place if the real desktop shows native Select All, Cut, Copy, Paste and Undo/Redo through both keys and right-click menus. Change a GNUstep binding and verify that the same operation follows the new binding. Check redo after grouped typing, completion and history, multiline input, IME, text drag, focus restoration, menu dismissal, zoom and the supported display densities. Use the packaged preview's normal launcher for visual review. Check native menus, browser chrome and ordinary web editing for regressions before removing existing paths.

The first implementation should use the pinned Linux builds and reuse the current host and original browser models. Perform this comparison before deciding which existing widget substitutions to retire or whether a maintained upstream adapter is worth pursuing.
