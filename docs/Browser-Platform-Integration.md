# GNUstep support across Chromium and Firefox

Use the browsers' existing Linux platform interfaces to provide GNUstep behavior across the entire application. Keep their engines and application models. Where the platform owns the presentation or interaction, call the existing GNUstep implementation through NativeUI. The bridge carries control state, native measurements and commands.

This covers browser windows and chrome, application and context menus, scrolling, webpage forms, shortcuts, editing, dialogs, built-in pages and DevTools. Each surface has a different integration point. The same GNUstep implementation should serve all of them and later be reusable by GTK and Qt adapters.

## How to build on the existing bridge

1. **Start with the existing desktop interfaces.** The FileChooser portal, Wayland window management and D-Bus application menu export already define their boundaries. Both Linux browsers can use XDG FileChooser, and Firefox can export its menubar. Keep these integrations and the current NativeUI providers. GTK and Qt clients can reuse the applicable desktop interfaces. [Chromium portal](https://chromium.googlesource.com/chromium/src/+/acca47dc0a9e6971232cf29c4482cc410740f278/ui/shell_dialogs/select_file_dialog_linux_portal.cc), [Firefox portal](https://github.com/mozilla-firefox/firefox/blob/main/widget/gtk/nsFilePicker.cpp), [FileChooser provider](../Libraries/NativeUI/Portal/README.md), [D-Bus menu bridge](../Experiments/DBusMenus/README.md)
2. **Use the browsers' platform seams for the rest.** Chromium's `LinuxUi` selects toolkit services and exposes edit-command matching, appearance and IME integration. Blink has a distinct form-theme and scroll interface. Firefox has a GTK widget backend, `NativeKeyBindings`, theme code and a preference-gated GTK context-menu model. Existing NEXTSPACE adapters already cover parts of these seams. Use the original models and transactions, and share GNUstep drawing, layout measurements and command interpretation in [NativeUI](../Libraries/NativeUI/README.md). A specialized editor can accept GNUstep commands while retaining its own word boundaries, multi-selection and undo grouping. [Chromium LinuxUi](https://github.com/chromium/chromium/blob/main/ui/linux/linux_ui.h), [Linux toolkit factory](https://github.com/chromium/chromium/blob/main/ui/linux/linux_ui_factory.cc), [Firefox GTK native menus](https://github.com/mozilla-firefox/firefox/blob/main/widget/gtk/NativeMenuGtk.cpp)
3. **Treat each control according to what must match.** Use real GNUstep menus, panels and tracking wherever NEXTSPACE behavior depends on them. Use GNUstep drawing and sizes for standard visible controls, with the browser supplying label, state and bounds. Pass shared system values such as colors and fonts where the browser retains rendering. Preserve a site's explicit rendering choices and keep layout, hit testing and painting on the same geometry at every supported scale. [NativeUI provider](../Libraries/NativeUI/README.md), [Existing scrollbar adapters](../Libraries/ForeignScrollers/README.md)

GNUstep's AppKit compatibility makes it the right implementation for these services. The macOS backends are built for Apple frameworks and windowing. Use their division of responsibilities with the Linux backends, which already expose comparable boundaries. Standard desktop interfaces carry over to compatible stock builds. Private browser interfaces require exact-build qualification or a maintained upstream integration. The current preview targets Debian ARM64 Chromium 156.0.8078.79 and Firefox ESR 153.6.0. Confirm the actual call path on those builds separately from reading upstream architecture. [GNUstep compatibility](https://www.gnustep.org/resources/documentation/Developer/Gui/Reference/index.html), [Firefox Cocoa build](https://github.com/mozilla-firefox/firefox/blob/main/widget/cocoa/moz.build), [Chromium pin](../Experiments/ChromiumScrollers/README.md), [Firefox pin](../Experiments/FirefoxNativeUI/source-audit.json)

Linux theming is useful for system colors, fonts and some metrics. Chromium's GTK integration mainly extracts colors. Firefox's GTK look-and-feel code supplies system values separately from Gecko's form drawing. NEXTSPACE also needs native presentation and behavior where those values cannot express it, including its left gutter, scrollbar tracking, detached menus and the actual picker panels. [Chromium GTK theme](https://chromium.googlesource.com/chromium/src/+/main/docs/linux/gtk_theme_integration.md), [Firefox GTK look and feel](https://github.com/mozilla-firefox/firefox/blob/main/widget/gtk/nsLookAndFeel.cpp)

## Compare across the whole browser before replacing any path

Run both pinned browsers alongside the existing preview baseline. Verify one complete route through each shared service, including actual user input and visual comparison.

- **Browser chrome and application menus:** switch windows by their title bars and verify borders, shadows, minimize and restore. Check that only the active app menu shows and exercise New Tab, focus address bar and editing commands. Change one desktop binding and verify that the corresponding action follows it.
- **Forms and scrollbars:** check buttons, checks, radios, progress, ranges, search, text, password and multiline fields, numbers, inline date/time editors and lists. Verify native metrics, left scrollers on pages and nested controls, arrow/drag/wheel behavior, CSS overrides, accessibility and normal form events.
- **Menus and panels:** open context menus on links, selected text, inputs, the address bar and browser UI. Check nested menu actions and cancellation, select popups, native calendar/color/file panels and repeated activation without stale focus or state.
- **Built-in UI and DevTools:** verify shared controls on settings, bookmarks, downloads and extensions. Check console, inspector and other relevant developer surfaces for coherent layout, native commands and context menus. Test clipboard, undo/redo, composition and autocomplete in their owning editors.
- **Geometry:** exercise zoom, resize and 100%, 125%, 150%, 175% and 200% through the ordinary graphical preview. Use browser and native window coordinate conversions rather than offsets per scale.

Keep the checkpoint as a baseline. Consolidate or retire existing substitutions individually when the equivalent native presentation and behavior are demonstrated. This is a whole-browser proposal. Its implementation and runtime comparison are still pending.
